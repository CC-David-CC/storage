# Opt-in verified content adapter

This isolated candidate keeps the existing mirror IndexedDB row authoritative.
It accepts an optional account-bound `VerifiedContent` instance, backed by
the research OPFS worker. New saves capture and verify an immutable generation
before their mirror row is published. `migrateContent(path, expectedVersion)`
explicitly captures a legacy Blob or ArrayBuffer and CASes the same row while
retaining the current metadata, including pending, conflict, move and attempted
state. Copying a file shares the immutable generation. Legacy records remain
readable. A scope must be the stable issuer plus account identifier, not a
username or login session; same-origin JavaScript can still access both stores.

This is **not ready for deployment**. Existing guarded tabs cannot understand
OPFS references. Do not enable the adapter until all potentially active clients
are coordinated and a new guarded floor prevents incompatible old clients.
Current server downloads still install Blobs; the adapter does not yet stream
remote results directly to OPFS. The worker bounds its processing slices, not
whole-browser memory. Published OPFS generations (including abandoned
references) are retained indefinitely; no production garbage collector or
cross-store physical power-loss atomicity is claimed. The mirror owns its supplied content instance exclusively and closes it on
session closure or detected account invalidation; never share an instance across mirrors. Production packaging must
include `verified-content.mjs` and the entire `opfs/` directory and enforce
the existing CSP. A returned File cannot be revoked after account change.
Real server, concurrent-device, fault and memory tests remain required.

On R730, local tests used Node 24.22.1, fake-indexeddb 6.2.4 and
puppeteer-core 24.31.0. `tests/mirror-verified-content.test.mjs`,
`tests/mirrored-files.test.mjs`, and `tests/mirror-archive-worker.test.mjs`
passed; `tests/mirror-opfs-browser.test.mjs` passed with Chromium and a
disposable loopback profile, exercising legacy migration, save, close/reopen,
copy and deletion. Unit tests include a concurrent edit during migration. This
does not prove browser process-kill recovery of the integrated adapter, physical
power-loss safety, server sync or a total browser-memory bound.

## Signed adapter and bounded-read follow-up

A preliminary set of signed runs used overlapping disposable Caddy fixtures and was provisional. After stopping those fixtures, verifying the served mirror SHA against source, and using a single isolated issuer/gateway, the dd8/44da signed gateway plus Chromium passed three consecutive
runs of `tests/mirror-opfs-signed.test.mjs`: signed create/replace and reopen,
cross-account denial, remote/local conflict preservation, and an injected lost
committed reply followed by a newer local edit. This is not an actual broken
TCP test for this adapter. A File returned by OPFS was intermittently rejected
by the gateway SDK even after slicing; wrapping it in a Blob passed the repeated
runs. No claim is made that the browser avoids copying internally.

`readBounded(path, limit, {signal})` now rejects promptly on caller abort while
waiting for the read, including an injected stalled content read. This does not
cancel the browser's underlying `Blob.arrayBuffer()` operation; its result is
discarded. Closing the session-owned content store is still required to stop its
worker. Full signed cancellation, conflict resolution, hard-crash and remote
download integration remain open.

## Experimental IndexedDB version floor and process crashes

When the optional OPFS content backend is enabled, the mirror opens the existing
mirror database at version 2, without changing the files store. An older
version-1 client receives versionchange and closes its connection, then cannot
reopen the version-2 database. The migration is origin-wide across accounts;
activation must coordinate every session and maintain a new rollback floor.
This does not protect against same-origin code deliberately opening version 2
and misinterpreting records. Browser UI must report an old tab's unsaved edit
rather than imply it was saved.

Chromium tests hold an old client in capture while a new client upgrades; the
old write fails with VersionError and no new row is created. A separate real
blocked upgrade test closes the blocker after the candidate rejected and checks
the abandoned request did not upgrade the database. Dedicated process SIGKILL
tests at (1) after verified OPFS candidate before mirror CAS and (2) after
mirror publication preserved the correct pending file on restart. A real
worker-backed hang test confirms explicit read cancellation and mirror close
each terminate their own worker. These are not physical power-loss or
cross-store atomicity guarantees.

The corrected isolated fixture also passed two independently stored Chromium
browser sessions signed into the same account: both edited offline, and after
A synced, B detected a conflict while retaining both B's local and A's server
bytes. This is not evidence of arbitrary WAN failure. A reentrant cancellation
test confirms that if the worker factory itself aborts the caller signal, no
worker message is dispatched and that worker is terminated.

## Snapshot leases and memory

The optional mirror exposes `acquireSnapshot(path,{signal})` returning
`{data,version,sha256,status,release}`. Each OPFS reader holds a shared Web
Lock on its account-scoped generation until the caller explicitly releases it.
After a snapshot is handed out, mirror close or later signal abort does not
revoke its lease; tab death releases the browser lock. Internal signed uploads
and changed-download base reads use leases and release in finally. Existing
`readBlob` is compatibility-only: a worker copies verified data into an
independent Blob, then releases its lease. This can require substantial memory.
The existing byte reads also go through the independent-copy path.

Real Chromium tests show an exclusive generation lock is unavailable while a
different tab holds a snapshot, remains unavailable after its mirror closes, and
becomes available after that tab closes. A detached compatibility Blob remained
readable after its original OPFS generation was explicitly removed. These are
cooperating-tab tests, not proof of arbitrary external consumers or power loss.
There is still **no published-generation collector**: safe deletion must
serialize all operations that introduce references, take the exclusive generation
lock, and transactionally recheck every authoritative current, previous,
conflict, attempt and moving reference. Do not assume a simple scan then delete
is race safe.

A 128 MiB isolated signed test with one guaranteed changed byte recorded 57.7 s
for initial save/sync and 71,470 bytes of changed-upload request bodies;
sampled summed Chrome RSS peaked at 1,292,800,000 bytes. These samples count
shared pages multiple times and exclude TLS/auth/network overhead. This
measurement predates snapshot lease integration, is not comparable to other
runs as a benchmark, and establishes no hard browser memory bound.

## Bounded worker verification and read lifetime

Workers check a generation's exact expected size and the 128 MiB ceiling
immediately after opening it, before hashing or copying. A real Chromium test
truncated a small file to 129 MiB and verified a Corrupt result with no worker
progress messages. Generation lock acquisition has a finite deadline; a
different tab holding the exclusive lock causes StorageUnavailable/lock-timeout
without disturbing that holder. This deadline applies only to waiting; an
already returned lease has no forced expiry.

read/readBounded acquire the immutable snapshot, materialize their byte result
once and release it after the browser's actual Blob read settles, including if
the caller stops waiting. The browser's native arrayBuffer operation cannot be
cancelled, so releasing its lock immediately on abort would be unsafe. A
detached compatibility readBlob still requires a worker-side copy.
